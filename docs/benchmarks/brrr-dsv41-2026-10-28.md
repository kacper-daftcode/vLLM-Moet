# Fraser Price's BRRR bench on vLLM-Moet's served DeepSeek-V4.1-Flash — 2026-10-28

Answer to [0xSero's question](https://x.com/0xSero/status/2114772773260382580) in Fraser Price's thread
([the request](https://x.com/fraserpricee/status/2114773506538053763): run `bench.py` so the numbers are comparable).
The script is `src/brrr/bench.py` of [`fraserprice/DeepSeek-4.1-Flash-1017-BRRR`](https://huggingface.co/fraserprice/DeepSeek-4.1-Flash-1017-BRRR)
(sha256 of the file as run: `f0248bdd842b…`), **unmodified**, invoked through a two-line runner that calls its cyclopts `app()`
(the module has no `__main__`; the repo runs it as a console script). Defaults: calibrated code prompt of 2048 / 16384 / 65528
tokens, five rounds per cell, **temperature 1.0, top-p 1.0, thinking off**, generation to natural EOS capped at 2,048 tokens,
the hottest GPU cooled to 70 °C before every round; PP from a `max_tokens=1` pass, TG from a prefix-cached second pass timed
while every stream decodes and none has finished.

## The server (production, as it served that night)

- 4× RTX PRO 6000 Blackwell Workstation Edition (96 GB each), 400 W power limit, GDDR7 +5000 MHz, PCIe 5.0 x16 each, no NVLink;
  the four cards of one NUMA node of a Threadripper host; driver 610.43.02.
- Image `vllm-moet-sm120:dsv41-nightly-df3bd094-r21-mxfp8` = vLLM nightly `df3bd094` (0.32.1rc1) + FlashInfer 0.7.2 + the
  vLLM-Moet sm_120 line (steps 17–39: fused decode MoE, sparse-MLA gather, P2P all-reduce, mHC boundary kernels, …; the same
  sources as `main` @ `9bb2199`, built by `Dockerfile.sm120-dsv41-nightly` as `-r22`).
- TP4, DSpark k = 7 (`rejection_sample_method: block`, exact verification), `--max-num-seqs 8`, `--max-num-batched-tokens 4096`,
  `--max-model-len 524288`, `--gpu-memory-utilization 0.94`, NVFP4 KV (9.62M tokens on the GPUs) + a 64 GiB host offload
  region + a disk tier, MXFP4 indexer KV, `INDEXER_TP_SHARD_MIN_ROWS=2048`; runtime switches as in the README's reproduce block
  plus `VLLM_MOET_MHC_MXFP8=1 VLLM_MOET_MHC_SIDE_DEFER=1 B12X_DYNAMIC_DETERMINISTIC_OUTPUT=1`; `--enable-prompt-tokens-details`
  (the script needs `usage.prompt_tokens_details.cached_tokens`; without the flag vLLM omits it and the script stops).
- The other four cards of the host carried an unrelated GLM-5.3-Flash A/B at the time (its own weights and KV offload on the
  same host RAM); production took no other traffic during the run.

## Command

```bash
# client in a container that sees GPUs 0-3 only: the script's cool-to-70°C gate reads every GPU nvidia-smi shows
docker run --rm --network host --gpus '"device=<the four UUIDs of GPUs 0-3>"' \
  -v $PWD/bench:/bench:ro -v $PWD/wheels:/wheels:ro --entrypoint bash vllm-moet-sm120:dsv41-nightly-df3bd094-r21 -c \
  'pip install -q --no-index --find-links /wheels cyclopts; python3 -u /bench/brrr_run.py -p 8001 -c 1 4 8 -r 5'
# brrr_run.py:  import sys; sys.path.insert(0, "/bench"); from bench import app; app()
```

`-c 1 4 8`: the 16-stream column is not run — production serves `--max-num-seqs 8`, and the script's decode window needs every
stream decoding at once (it raises when one finishes before all have started). Everything else is the script's default.

## Reading it next to our own numbers

- Single stream, TG p50 **766 / 750 / 744 tok/s** at 2K / 16K / 65K of context: the decode rate barely moves with context
  (sparse attention + NVFP4 KV); our greedy single-prompt Fraser bench on the same server gives 679 tok/s median over 40 reps
  (740 best) at 128.4 engine steps/s — the gap is the acceptance rate, not the step rate.
- Eight streams: **~1,900 tok/s** aggregate (TG total 1,866–1,960), ~240 tok/s per stream; four streams ~1,350 aggregate.
- Prefill: 17.5K tok/s on a single 65K prompt (PP total 16–18K tok/s at 4 and 8 streams of 16K–65K); the 2K prompts are
  launch-bound (9.1–14.2K tok/s). TTFT p50 221 ms at 2K, 1.03 s at 16K, 3.74 s at 65K.
- Not measured here: 16 streams (see above) and thinking on (`-k 50/75/100`: uncapped generation).
