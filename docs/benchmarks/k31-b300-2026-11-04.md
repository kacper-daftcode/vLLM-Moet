# Kimi-K3.1-Pro + DSpark on 8× B300 — 2026-11-04/05: the k sweep, the specialized decode path into production, DCP / EP / drafts

The night hgx-02 went from Kimi-K3 to Kimi-K3.1-Pro, measured on real weights with the probes of `tools/k3_b300/`
(single-stream `k3_code_bench.py` at `reasoning_effort: low`, `k3_matrix.py` 8K prompts at C=32/64, `gsm8k_probe.py` 200
questions at C=16, `prefix_probe.py` 30K resend, `multiturn_accept.py` 16K agent session, `capacity_probe.py` 128 × 15K).
The headline: the day-0 image's `latency_specialized` decode path, once its persistent experts grid fits a 148-SM B300,
decodes a single stream 1.77× faster than the stock path at the same acceptance, GSM8K and prefix hits.

## The server

- HGX B300: 8× B300 SXM6 (275 GiB HBM3e, **148 SMs** — GB300 has 152), 2× Xeon 6767P, NVLink 5 / NVSwitch (NV18), driver
  615.71.09, Fabric Manager + NVLSM; `/data` = RAID0 of 8 NVMe (models, the KV offload slabs, the JIT caches).
- Image `vllm/vllm-openai:kimi-k31` (vLLM `0.1.dev24216+g266e88c05`, the K3.1 day-0 build: K3.1 missed v0.33.0) and, for
  the specialized path, `vllm-moet-b300:k31-266e88c0-r1` = the same image + `tools/k3_b300/patch_vllm_k31_experts_grid.py`
  (`Dockerfile.b300-k31`). Launcher `docker/b300/run-k3.sh`.
- Served configuration (`docker/b300/run-k3.sh`, the K3 arrangement carried over): TP8 + DCP8 (`--dcp-comm-backend a2a`),
  `--kv-cache-dtype fp8` (vLLM picks FLASHINFER_MLA_SPARSE for the DSA layers), prefix caching with `--prefix-match-unit
  128`, `SimpleCPUOffloadConnector` on its disk backend (12 TiB of slabs through the page cache), DSpark with
  `Inferact/Kimi-K3.1-Pro-DSpark-preview` (5 dense MLA layers, its own FP8 cache on FLASHINFER_MLA), block verification,
  probabilistic drafting, `--use-replayssm` (KDA RecoverSSM), `--max-num-seqs 128`, `--max-num-batched-tokens 8192`,
  `--max-cudagraph-capture-size 512`, the V2 model runner, the Python API server (Anthropic Messages API and vision),
  `--gpu-memory-utilization 0.95`. The model: `moonshotai/Kimi-K3.1-Pro` (revision `6d0a020`), MXFP4 experts, 69 KDA +
  24 Gated-DSA layers, 896 experts top-16, 1M context.
- The draft in the Inferact repository is the weaker "step 3 500" checkpoint of 2026-11-03 (per-position acceptance at
  k=5: 0.61 / 0.34 / 0.18 / 0.10 / 0.06), so every K3.1 row below has an accepted length around 2.2 where K3's RedHat
  draft had 4.1: the step rates, not the tok/s, compare the kernels.

## The specialized decode path on B300 (`latency_specialized`, 22:29–23:15Z)

`--additional-config '{"decode_backend":"latency_specialized"}'` did not start on the kimi-k31 image:

```
RuntimeError: Kimi K3 MoE experts: 152 CTAs cannot be co-resident (1 per SM x 148 SMs)
```

`PersistentExperts` (`models/kimi_k3/nvidia/specialized_decode/cutedsl/moe/experts_runtime.py`) sizes its per-batch
grid table on GB300 ("grouped B9-64 on 152", "wide: every SM" = 152) and `check_residency` refuses a grid the device
cannot hold at once. The kernel splits its work by its grid (`cta * count // self.grid` slices, a grid-wide claim
counter for the FC2 tail, 160 counters re-armed for any grid) and asserts only `grid >= capacity`, so the patch caps the
table and the default grid at `multi_processor_count` (GB300 unchanged). With it the path starts: the init (providers,
KV binding, JIT warmup, FULL graphs to 512) takes 669 s on dummy weights, 1 230 s to `/health` on real weights (the
stock path: 440 s) — the CuTe DSL kernels compile at every start (the DSL's file cache under `/tmp` is not persisted).

Steps up to 64 rows (16 requests × 4 verify tokens) run the whole specialized step; 64–320 rows run the stock layer
loop with the specialized attention projection and cores (C=32 = 128 rows, C=64 = 256); wider steps and every prefill
run stock. The step on dummy weights: 111 steps/s (9.0 ms) against the stock path's 65 steps/s with k=3 verification.

### Where the stock step goes (torch profiler, rank 0, 2.5 s of decode, `profile_decode.py`)

| | C=1 (4 tokens per step) | C=32 (128 tokens per step) |
|---|---|---|
| wall per step (profiler on) | 17.5 ms | 35.4 ms |
| kernel launches per step | **2 995** (median 5.1 µs; 1 482 under 5 µs) | 3 090 (median 7.7 µs) |
| main stream busy | 8.6 ms (49%) | 14.2 ms (40%) |
| MoE experts (TRT-LLM MXFP4 bmm FC1/FC2, routing, quant, SiTU) | 4.2 ms | 11.9 ms |
| dense GEMMs / norms (skinny GEMM, nvjet, dot-prod, split-K reduce) | 6.0 ms | 9.5 ms |
| latent MoE tail (lamport multicast all-reduce + norm) | 1.9 ms | 6.6 ms |
| other communication (oneshot all-reduce 96 × 26 µs, NCCL all-gather, DCP gathers) | 3.8 ms | 4.5 ms |
| DSA attention + indexer (prims_ts decode 24 × 9 µs, indexer logits, top-k, a-GEMMs) | 3.8 ms | 5.6 ms |
| KDA (RecoverSSM verify 69 × 8 µs, conv, gated norm) | 0.9 ms | 3.8 ms |

At batch 1 the stock step is launch- and synchronization-bound: ~3 000 kernels of a few microseconds over 93 layers,
the single largest item the all-reduce after attention (2.5 ms of waiting for the slowest rank), the sparse attention
itself 0.2 ms. That is the gap the specialized path closes with its persistent per-layer kernels and mailboxes.

### The specialized step (same capture)

| | C=1 (4 tokens per step) | C=32 (128 tokens per step, the wide path) |
|---|---|---|
| wall per step (profiler on) | **12.2 ms** (8.7 ms without the profiler) | 34.5 ms (36.6 without) |
| kernel launches per step | **1 587** (988 + 314 + 280 on three streams) | 2 315 |
| dense GEMMs (`SplitKGemm` 94 × 40 µs, `OprojConsumer` 93 × 40 µs incl. the all-reduce wait, `warp_splitk`, `WsGemm`) | 12.9 ms of kernel time across the streams | 11.7 ms |
| MoE (`ExpertsKernel` 92 × 26 µs, `MoeTail` 92 × 13 µs, `RouteSitu`, `L2Prefetch`) | 4.5 ms | **36.9 ms**: `ExpertsKernel` 92 × 195 µs and `wide.Finalize` 92 × 190 µs on two streams |
| DSA attention + indexer (`DcpValue`, `IndexerScore`, `SparseDcpDecode`, `MlaQuery`, `IndexFront`) | 1.9 ms | 4.1 ms |
| KDA (`KdaSplit` 69 × 6 µs) | 0.5 ms | 2.1 ms (`KdaFusedWS` 69 × 29 µs) |
| communication outside the mailboxes | 0.4 ms (2 oneshot all-reduces) | 4.6 ms (twoshot all-reduces 220 per step, `GemmRsAr`) |

At batch 1 the step is 93 chains of projection → attention → o-proj mailbox all-reduce → route → persistent experts →
tail, ~94 µs per layer against a weight-bandwidth floor near 9 µs (16 of 896 experts × 2.06 MB per rank): still
latency-bound, now by the chain's hand-offs rather than by 3 000 launches. At 128 rows the persistent experts kernel
sits on the HBM roofline: 128 tokens × 16 routes touch ~805 distinct experts per layer, each rank streams ~1.66 GB of
its shards (896 experts × 2 × 3072 × 3584 + 3584 × 3072 MXFP4 weights, 1/8 of every expert per rank), 207 µs at
8 TB/s against the 195 µs measured — an 18 ms per step floor for the MoE alone that no TP/EP layout changes (expert
parallelism moves whole experts between ranks, the bytes per rank per touched expert stay), only more tokens per step
amortize it. The rest of the wide step (dense GEMMs 11.7 ms, the all-reduces 4.6 ms, attention 4 ms of kernel time
over two streams) and, above all, the draft's accepted length are the levers at C ≥ 32.

DCP=1 buys 5% of step rate for 7.6× less KV (two 1M requests fit), EP over MegaMoE loses a third of the step rate at
batch 1 and ties at C=32 — as the roofline above says, the expert bytes per rank do not change with the layout at these
batch sizes. Neither competes with the specialized path's 1.77× at the full KV pool.

## The gates on the image, and production (01:31–02:17Z)

The same battery on `vllm-moet-b300:k31-266e88c0-r1` itself (no bind mount), `DECODE_BACKEND=latency_specialized`, k=3:
code at T=1 / top-p 0.95 **264.3 tok/s** (accepted 2.34, 112.8 steps/s; the stock path's best T=1 row, k=5, 130.8),
prose at T=1 259.7; needle 30K and 100K at depths 0.2 / 0.7 all PASS; response fields and tool calls in both modes OK;
vision over chat completions and `/v1/messages` OK; the Anthropic Messages API probe 7/7 groups; 128 concurrent ~10K-token
requests with 3 000 output tokens each: 128 running at once, peak KV 38.6%, 0 preemptions, 2 516 tok/s aggregate; the
greedy outputs against the stock k=5 reference share 213 / 210 / 50 / 553 leading characters on the four prompts (0 of 4
identical — the stock FP8 configurations of the window differed from one another by as much). The host's serving
wrapper switched to the image and the decode backend at 01:56Z; the server answered `/health` at 02:16:30Z (20.5 min),
the smoke probes passed (tool calls, 242 tok/s on the code prompt), and the watchdog's start grace went from 30 to 40
minutes for the longer start. Rollback is the previous wrapper (the stock path on the official image).
