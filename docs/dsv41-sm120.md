# DeepSeek-V4.1-Flash on 4× RTX PRO 6000 (sm_120)

The official checkpoint ([`deepseek-ai/DeepSeek-V4.1-Flash-1017`](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017):
552B + a 196B Engram table, MXFP8 dense, MXFP4 experts, 510 GB) served on four RTX PRO 6000 (96 GB,
PCIe): TP4, 512K context, DSpark speculative decoding (k = 7), vision, thinking, tool calling, KV
offload to host RAM and disk.

The image is the official `vllm/vllm-openai` nightly (df3bd094: FlashInfer 0.7.2, DeepGEMM 727f8470)
plus the sm_120 changes of [`Dockerfile.sm120-dsv41-nightly`](../Dockerfile.sm120-dsv41-nightly):
DeepGEMM rebuilt with its SM120 asserts fixed, anchored patchers on the installed vLLM / FlashInfer
(they refuse any other version), and CUDA extensions compiled into the image. Nothing is patched by
hand and nothing JIT-compiles at boot. What each change does and how it was measured:
[dsv41-sm120-internals.md](dsv41-sm120-internals.md).

## Requirements

- 4× RTX PRO 6000 Blackwell (an RTX 5090 does not fit the model at TP4; for 4× 5090 see the hybrid
  line), GPU peer-to-peer over PCIe (`NCCL_P2P_LEVEL=SYS` is set by the launcher; KVM guests with
  the cards on PCIe work).
- A driver with CUDA 13 support, Docker with the NVIDIA container toolkit.
- Host memory: the loader keeps ~280 GB in shared memory while serving, plus the KV offload region
  (64 GiB as served) — ~330 GB in total, one server per host. On a host with less RAM run with
  `KV_OFFLOAD_GIB=0`; below the GPU KV capacity (9.6M tokens) it changes nothing.
- Disk: the checkpoint (510 GB), ~30 GB for the image, a few GB of autotune cache (`CACHE_DIR`),
  the KV disk tier if used.

## Build

```bash
hf download deepseek-ai/DeepSeek-V4.1-Flash-1017 --local-dir /srv/models/DeepSeek-V4.1-Flash-1017
DOCKER_BUILDKIT=1 docker build -f Dockerfile.sm120-dsv41-nightly -t vllm-moet-sm120:dsv41-nightly-df3bd094-r26b .
```

~11 minutes after the base pull; the build needs network access (base image, DeepGEMM clone),
serving does not. Every step is a build argument (`--build-arg VLLM_MOET_<STEP>=0` leaves it out,
see the Dockerfile) and the image carries the result as `com.vllm-moet.*` labels. Verify the kernels
the image ships (every cubin round-trips through [cubit](https://github.com/kacper-daftcode/cubit)
bit for bit): `python3 tools/dsv41_sm120/cubit_gate.py IMAGE`.

## Serve

```bash
export IMAGE=vllm-moet-sm120:dsv41-nightly-df3bd094-r26b MODEL_DIR=/srv/models/DeepSeek-V4.1-Flash-1017 CACHE_DIR=/srv/cache/ds41
GPU_MEM_UTIL=0.92 docker/sm120/run-dsv41.sh      # first start, ~22 min: FlashInfer autotunes into CACHE_DIR (0.94 OOMs on an empty cache)
docker stop -t 60 ds41-flash
SERVED=1 GPU_MEM_UTIL=0.94 KV_OFFLOAD_GIB=64 KV_OFFLOAD_FS_DIR=/srv/kvcache KV_OFFLOAD_PROMPT_ONLY=0 \
  INDEXER_TP_SHARD_MIN_ROWS=2048 docker/sm120/run-dsv41.sh                     # later starts ~7 min; the served configuration
```

`SERVED=1` is the reference configuration: `--moe-backend b12x`, DSpark k = 7 and the runtime
switches of the table below in their *served* state. The API is OpenAI-compatible on
`127.0.0.1:8001` (`BIND=` publishes it — put an authenticating proxy in front). Every knob is an
environment variable documented in the header of [`docker/sm120/run-dsv41.sh`](../docker/sm120/run-dsv41.sh).

Operations: vLLM never deletes the disk tier's files — run [`docker/sm120/kvcache-ttl.sh`](../docker/sm120/kvcache-ttl.sh)
from cron; [`docker/sm120/ds41-watchdog.sh`](../docker/sm120/ds41-watchdog.sh) restarts a crashed
server (the containers run with `--restart no` so that maintenance can replace them). A change of
the prefill's arithmetic (steps 40–41 below) invalidates the disk tier: give it a new directory.

## Validate

```bash
curl -s 127.0.0.1:8001/health
python3 tools/sm120_perf/decode_bench.py http://127.0.0.1:8001 deepseek-ai/DeepSeek-V4.1-Flash '{"thinking": false}'
python3 tools/sm120_perf/needle_any.py http://127.0.0.1:8001 deepseek-ai/DeepSeek-V4.1-Flash '{"chat_template_kwargs": {"thinking": false}}' 30000,100000
python3 tools/sm120_perf/fraser_bench.py --base http://127.0.0.1:8001 --model deepseek-ai/DeepSeek-V4.1-Flash \
  --prompt-file tools/sm120_perf/fraser_prompt.txt --reps 40
```

Expected with `SERVED=1` at 400 W: 128–130 steps/s on short prompts, Fraser 680–690 tok/s median
over 40 reps, needle PASS. The log should show `Using MXFP4 indexer cache for Lightning Indexer`
and `GPU KV cache size: 9,6xx,xxx tokens` at `GPU_MEM_UTIL=0.94`. If steps/s are ~10 % low and the
log shows NCCL on `SHM`, P2P is not available (IOMMU / ACS settings). Op-level tests of every kernel
run inside the image on one GPU: [`tools/dsv41_sm120/README.md`](../tools/dsv41_sm120/README.md).

## Known limits

- With the disk tier, each request pays ~20 ms more before its first token (cause open).
- TP8 with a 1M window on eight cards was validated at the bring-up, not on this image.
- `enable_adaptive_verification` must stay `false` (the indexer backend does not support it on sm_120).
- DSpark k = 7 pays for itself on code and single streams; in mixed traffic with low acceptance a
  smaller `SPEC_TOKENS` is the lever.
- The pipelined prefill (step 47) is power-bound at 400 W on the reference host: ~385 W and a median SM clock of
  ~2.0 GHz through the sequence-parallel phase with GDDR7 at +5000 MHz, −14 % at 163K where the second host (GDDR7 at
  12.5 GHz, SM up to 2.43 GHz) measures −22.6 %. A higher power limit or a smaller memory offset is unmeasured.
- `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0` (vLLM's memory-profiler knob) with `PREFILL_PIPE=2`: the allocator
  churns (+11 % at 163K) and a 400K prompt runs out of memory — leave vLLM's default.
- With the host KV tier, on a KVM-guest host the four TP workers' `cudaHostRegister` of the shared offload region
  (the whole range in one `pin_user_pages`, all four at the same moment) failed for three of them at every start
  (`host_register failed … the offload region stays pageable` in the log); a pageable rank's stores are
  host-synchronous, and when rank 0 — the only writer of the TP-replicated MLA KV — is one of them, it blocks
  211–219 ms per 8 192-token step under load (86 ms per-step head against 1.5 ms when it is pinned). The reference host
  registers 4/4. The fix — the registration under a cross-process lock in rank order, in chunks, and a pageable rank's
  copies staged through pinned memory on a transfer stream (`tools/dsv41_sm120/kv_offload/`,
  `VLLM_MOET_KV_SWAP_ASYNC=1`: 4/4 registered, 1.5 ms head) — is not yet an image step.
