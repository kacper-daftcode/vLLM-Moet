# DeepSeek-V4.1-Flash on 4× RTX PRO 6000 (sm_120)

The official checkpoint ([`deepseek-ai/DeepSeek-V4.1-Flash-1017`](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017):
552B + a 196B Engram table, MXFP8 dense, MXFP4 experts, 510 GB) served on four RTX PRO 6000 (96 GB,
PCIe): TP4, 512K context, DSpark speculative decoding (k = 7), vision, thinking, tool calling, KV
offload to host RAM and disk.

The image is the official `vllm/vllm-openai` nightly (df3bd094: FlashInfer 0.7.2, DeepGEMM 727f8470)
plus the sm_120 changes of [`Dockerfile.sm120-dsv41-nightly`](../Dockerfile.sm120-dsv41-nightly):
DeepGEMM rebuilt with its SM120 asserts fixed, anchored patchers on the installed vLLM / FlashInfer
(they refuse any other version), and CUDA extensions compiled into the image. Nothing is patched by
hand and nothing JIT-compiles at boot. What each change does and how it was measured:
[dsv41-sm120-internals.md](dsv41-sm120-internals.md).

## Requirements

- 4× RTX PRO 6000 Blackwell (an RTX 5090 does not fit the model at TP4; for 4× 5090 see the hybrid
  line), GPU peer-to-peer over PCIe (`NCCL_P2P_LEVEL=SYS` is set by the launcher; KVM guests with
  the cards on PCIe work).
- A driver with CUDA 13 support, Docker with the NVIDIA container toolkit.
- Host memory: the loader's pinned tables take 264.3 GiB of shared memory while serving, 189.0 GiB with
  the allocator variable that `SERVED=1` sets; the KV offload region comes on top (64 GiB as served:
  253.0 GiB in total), one server per host. On a host with less RAM run with `KV_OFFLOAD_GIB=0`; below
  the GPU KV capacity (6.14M tokens as served) it changes nothing.
- Disk: the checkpoint (510 GB), ~30 GB for the image, a few GB of autotune cache (`CACHE_DIR`),
  the KV disk tier if used.

## Build

```bash
hf download deepseek-ai/DeepSeek-V4.1-Flash-1017 --local-dir /srv/models/DeepSeek-V4.1-Flash-1017
export IMAGE=vllm-moet-sm120:dsv41-nightly-df3bd094-r32      # the served image; also the launcher's default
DOCKER_BUILDKIT=1 docker build -f Dockerfile.sm120-dsv41-nightly -t $IMAGE .
```

~11 minutes after the base pull; the build needs network access (base image, DeepGEMM clone),
serving does not. The served image is this Dockerfile at commit `3e3d519`; a build of the current tree
also carries what the [changelog](../CHANGELOG.md) lists under "In the tree after `-r32`", all of it
off by default. Every step is a build argument (`--build-arg VLLM_MOET_<STEP>=0` leaves it out,
see the Dockerfile) and the image carries the result as `com.vllm-moet.*` labels. Verify the kernels
the image ships (every cubin round-trips through [cubit](https://github.com/kacper-daftcode/cubit)
bit for bit): `python3 tools/dsv41_sm120/cubit_gate.py IMAGE`.

## Serve

```bash
export MODEL_DIR=/srv/models/DeepSeek-V4.1-Flash-1017 CACHE_DIR=/srv/cache/ds41      # IMAGE: as built above
GPU_MEM_UTIL=0.92 docker/sm120/run-dsv41.sh      # first start, ~22 min: FlashInfer autotunes into CACHE_DIR (0.94 OOMs on an empty cache)
docker stop -t 60 ds41-flash
SERVED=1 GPU_MEM_UTIL=0.94 KV_OFFLOAD_GIB=64 KV_OFFLOAD_FS_DIR=/srv/kvcache KV_OFFLOAD_PROMPT_ONLY=0 \
  INDEXER_TP_SHARD_MIN_ROWS=2048 docker/sm120/run-dsv41.sh                     # later starts ~9 min; the served configuration
```

`SERVED=1` is the reference configuration: `--moe-backend b12x`, DSpark k = 7 and the runtime
switches of the table below in their *served* state. The API is OpenAI-compatible on
`127.0.0.1:8001` (`BIND=` publishes it — put an authenticating proxy in front). Every knob is an
environment variable documented in the header of [`docker/sm120/run-dsv41.sh`](../docker/sm120/run-dsv41.sh).

Operations: vLLM never deletes the disk tier's files — run [`docker/sm120/kvcache-ttl.sh`](../docker/sm120/kvcache-ttl.sh)
from cron; [`docker/sm120/ds41-watchdog.sh`](../docker/sm120/ds41-watchdog.sh) restarts a crashed
server (the containers run with `--restart no` so that maintenance can replace them). A change of
the prefill's arithmetic (steps 40–41 below) invalidates the disk tier: give it a new directory. The
served prefill numbers are with the CPU frequency governor `performance` on the server's cores: against
`schedutil` a fresh prefill is 5.49 % shorter at 163K and 16.9 % at 19K, decode unchanged
([record](benchmarks/dsv41-sm120-steps-2026-11-10.md#as-served)).

## Switches

rebuild). *Bits*: whether the output is bit-identical to the path it replaces. *Served*: the state
under `SERVED=1`. A row says what a step does and gives its headline number; the mechanism of the
longer steps is in [the internals](dsv41-sm120-internals.md#steps-in-detail), their measurements with
the conditions in [the record](benchmarks/dsv41-sm120-steps-2026-11-10.md), the image that brought a
step in the [changelog](../CHANGELOG.md).

Steps 7 and 9 (the SWA bounded replay, the fused query-norm + quantization gate) are vLLM's own in
this base. `B12X_DYNAMIC_DETERMINISTIC_OUTPUT=1` (b12x's own switch, set in the image) makes the
MoE sum deterministic above 8 tokens.

As served, the second cubin of step 46b is `sparse_mla_prefill_v43b.cubin`: it is loaded for the A/B
facility of step 42b, compared once with the shipped cubin, and never selected — its key stays 0.
`v43b`, `v43` and `v42` must not be selected: on one path each rewrites the data registers of a
shared-memory store before anything has waited on that store
([why](dsv41-sm120-internals.md#step-46b--two-cubins-of-the-attention-kernel)).

### Sub-switches

What selects a variant inside a step: its default in the image and its state under `SERVED=1`. A `key`
is a key of step 42b's control file, not an environment variable; while the file is not read, the
environment's value applies. As served there is no control file, and a key's `served` cell is the state
its ranks report. The last row is not a switch of a step: PyTorch's own allocator variable, which
`SERVED=1` sets.

```bash
curl -s 127.0.0.1:8001/health
python3 tools/sm120_perf/decode_bench.py http://127.0.0.1:8001 deepseek-ai/DeepSeek-V4.1-Flash '{"thinking": false}'

```

Expected with `SERVED=1` at 400 W: 128–130 steps/s on short prompts, the Fraser bench at 127–129
steps/s with a tok/s median that follows the acceptance of its runs (671.5 over 40 reps on `-r32`,
646–696 in series of 5–15), needle PASS. The log should show `Using MXFP4 indexer cache for Lightning Indexer`
and `GPU KV cache size: 6,1xx,xxx tokens` at `GPU_MEM_UTIL=0.94` (`9,6xx,xxx` with `PREFILL_PIPE=0`).
If steps/s are ~10 % low and the log shows NCCL on `SHM`, P2P is not available (IOMMU / ACS settings).

## Known limits

- With the disk tier, each request pays ~20 ms more before its first token (cause open).
- TP8 with a 1M window on eight cards was validated at the bring-up, not on this image.
- `enable_adaptive_verification` must stay `false` (the indexer backend does not support it on sm_120).
- DSpark k = 7 pays for itself on code and single streams; in mixed traffic with low acceptance a
  smaller `SPEC_TOKENS` is the lever.
- The pipelined prefill (step 47) is power-bound at 400 W on the reference host: ~385 W and a median SM clock of
  ~2.0 GHz through the sequence-parallel phase with GDDR7 at +5000 MHz, −14 % at 163K where the second host (GDDR7 at
  12.5 GHz, SM up to 2.43 GHz) measures −22.6 %. A higher power limit or a smaller memory offset is unmeasured.
- `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0` (vLLM's memory-profiler knob) with `PREFILL_PIPE=2`: the allocator
  churns (+11 % at 163K) and a 400K prompt runs out of memory — leave vLLM's default.
- With the host KV tier on a KVM-guest host, the TP workers' `cudaHostRegister` of the shared offload region can
  fail (`host_register failed … the offload region stays pageable` in the log), and a pageable rank's stores are
  host-synchronous. Step 48 (`VLLM_MOET_KV_SWAP_ASYNC=1`, off by default) is the fix; the reference host registers
  4/4 without it.
